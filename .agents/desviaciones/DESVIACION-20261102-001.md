# Bloqueo de binarios durante la actualización de dependencias

## Qué se esperaba

El apartado §17.0.3 requiere evidencia ejecutada sobre las dependencias finales.
La actualización y `npm ci` deben completarse antes de acreditar ese árbol.

## Qué se observó

La primera actualización terminó con código 0 y avisos `EPERM` al limpiar
binarios nativos antiguos. La regeneración posterior falló con `EBUSY` al copiar
el binario de Rollup. El proceso `node.exe` 55316 ejecutaba el CLI local de
Atomic UI con el argumento `serve`; la consulta se realizó antes de detenerlo.
La evidencia final no se acreditó sobre la instalación parcial.

## Evidencia

Los originales se conservan en
`C:/Users/cotaha/AppData/Local/Temp/atomic-deps-20261102/npm-update.log` y
`npm-update-final.log`.

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
  Where-Object { $_.CommandLine -like '*-Atomic-UI*' } |
  Select-Object ProcessId, ParentProcessId, CommandLine
```

```text
ProcessId: 55316
ParentProcessId: 57180
CommandLine: "node" "C:\Users\cotaha\source\repos\-Atomic-UI\node_modules\.bin\\..\@angular\cli\bin\ng.js" serve
EBUSY: resource busy or locked, copyfile
node_modules/@rollup/rollup-win32-x64-msvc/rollup.win32-x64-msvc.node
```

## Corrección mínima que preserva la doctrina

Se verifica la identidad del proceso 55316 y se detiene únicamente el servidor
de desarrollo de este proyecto. Después se regenera el lock, se ejecuta
`npm ci` y se repiten las validaciones sobre el árbol final. Se verifica
`npm start` en un puerto local de prueba y se cierra ese proceso propio.

## Lo que NO se debe hacer

No se detienen todos los procesos Node ni servicios de otros proyectos. No se
borran carpetas compartidas, no se relajan comprobaciones y no se declara
reproducible una instalación que falló. No se descarta el lock previo del usuario.

## Escalado

Se cerró el proceso identificado, la instalación limpia final terminó con
código 0 en 55 segundos y sin `EPERM` ni `EBUSY`, y el arranque posterior
respondió HTTP 200 en `http://127.0.0.1:4301/`. El proceso propio de prueba se
cerró después de la comprobación. Los originales `npm-ci.log`,
`npm-ci.exitcode.txt` y `arranque-http.json` acreditan la recuperación. No se
requirió detener otros procesos ni ampliar la corrección.
